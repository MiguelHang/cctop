# Processes

Code: `procs/`

- **The memory metric is cornercase's** (`design/memory.md` there): memory a process holds on its own. Linux: `RssAnon + VmSwap` from `/proc/<pid>/status`. macOS: `ri_phys_footprint` from `proc_pid_rusage` (Activity Monitor's Memory). Neither counts file-backed pages shared by every process (the binary, its libraries), so the sum over a tree is close to what it costs. RSS was rejected: cornercase measured it at about twice the real cost for Claude Code (its 224 MB binary counted once per process). For the same reason `sysinfo` is not the source: it reports RSS.
- **CPU %** is the change in user + system time between two samples divided by the wall time between them, per process (100 % = one core, as `top`). The first sample shows no CPU.
- **Environment**: Linux reads `/proc/<pid>/environ` (only the user's own processes are readable, which are the ones that matter). macOS reads `sysctl` `KERN_PROCARGS2`, which holds the arguments then the environment. Only `CORNERCASE_PANE`, `CORNERCASE_SERVER` and `CLAUDE_CONFIG_DIR` are kept.
- **One sample** lists every process of the user once (pid, parent, name, arguments, memory, CPU time, the kept variables). Processes of other users are skipped. A process that ends while being read is dropped, never an error.
- **Tests** of the real sources run on the test process: its pid is listed, a variable it set in a child is read back, and memory written to an anonymous mapping of 64 MiB raises the figure while a mapped file does not (the check cornercase uses). A process spinning 200 ms shows CPU above zero between two samples. The memory check measures the whole test process, so it reruns itself alone in a child test process (`--exact --ignored`, gated by `CCTOP_MEMORY_PROBE`): other tests allocating in parallel threads would make it flaky. These checks live once in `procs/probe.rs` and each platform's tests call them with its source. There is no macOS machine at hand: the macOS source is checked with `cargo clippy --target {x86_64,aarch64}-apple-darwin` on Linux and its tests run only on the macOS CI runner. To confirm on the first macOS run: that `KERN_PROCARGS2` of `/bin/sleep`, a platform binary under SIP, still returns its environment for the same uid (psutil relies on it), and that its `pbi_name` is `sleep`. If the child-variables check fails there, check first whether the environment comes back empty before touching the parser.
- **A reused pid** is told apart by the process's start time (`stat` field 22 on Linux), kept in `Process::started` as an opaque value only compared for equality. If the start time differs, or the CPU time went down, the process shows no CPU for that sample instead of a wrong figure.
- **Linux fields**: the owner is the owner of the `/proc/<pid>` folder, read from its metadata before any file inside it, so other users' processes cost one `statx` and nothing more (see the cost below); the parent, process group, user + system time and start time come from `stat`, converted with `sysconf(_SC_CLK_TCK)` (100 if it fails). The name is the one in `stat`, taken between the first `(` and the last `)` because it may hold spaces and parentheses; it is the same text as `comm`, so `comm` is not read again. Memory comes from `status` (`RssAnon + VmSwap`) only when something is swapped out (`SwapTotal` above `SwapFree` in `/proc/meminfo`, or the file unreadable); when nothing is, `VmSwap` is zero for every process and the kernel's `statm` gives the same `RssAnon` cheaper, as resident minus shared pages (file-backed and shmem) times the page size (`sysconf(_SC_PAGESIZE)`, 4096 if it fails). A page swapped out between reading `meminfo` and a process's `statm` is missed for that one sample. A process without `RssAnon` (kernel threads, zombies; in `statm`, a size of zero) has no memory (`—`); `status` and `stat` are read as bytes and decoded lossily, because a process may set any bytes as its name (`prctl(PR_SET_NAME)`) and must not vanish from the sample for it; one whose `stat` or memory file cannot be read or parsed is dropped; missing `cmdline` or `environ` leave the arguments empty and the variables unset. Empty variables count as unset.
- **Owner by the folder's metadata**: the folder belongs to the effective uid, and to root when a process is not dumpable (`prctl(PR_SET_DUMPABLE, 0)`, setuid programs such as `sudo`), where `status` gave the real uid. Such processes of the user are now skipped: they are no longer listed, even though their parent placed them in a pane before (a `sudo …` started in a shell, an `ssh-agent` or `gpg-agent` that does not daemonize). The saving was judged worth it, and none was found on the machine measured (all 131 of the user's processes had the folder as their own). Rejected for 0.1.0: reading `status` of root's folders whose parent is one of the user's processes, a second pass over the list.
- **Arguments and variables are read once per process**: `cmdline` and `environ` are kept from one sample to the next per pid together with the start time and the name from `stat`, and read again when either changes (a reused pid has another start time; an `exec` changes the name), and forgotten when the pid is not listed. A new process is read twice, in its first two samples, and only then kept: a sample can fall between a `fork` and the `exec` that follows it, when `cmdline` and `environ` are still the parent's and the name may not change (`bash` → `bash script.sh`, `node` → `node …/claude`, which would hide a `claude`); a process still between the two after a whole interval keeps the parent's until it ends. A process that rewrites its own arguments without an `exec` (`setproctitle`) or `exec`s a program with the same name keeps its old arguments in cctop until it ends; they are only shown, and the variables only change with an `exec`.
- **Cost of a sample** (measured 2026-10-21, Linux 6.8 on an 8-vCPU AMD EPYC VM, 58 panes, about 126 of the user's processes among 290; `CCTOP_CYCLE_STATUS=<a saved status --json> cargo test --release --lib cycle_cost -- --ignored --nocapture`, which samples, takes the CPU % and builds the tree 50 times): reading `status` of every process to learn its owner, then `stat`, `cmdline` and `environ` of the user's took 30 ms of CPU per sample. Owner from the folder: 16.6 ms. `std::fs::read` makes several small `read` calls on `/proc` files, which report a size of 0 (1,840 reads per sample): a 4 KiB buffer first, 12 ms. `statm` instead of `status` when nothing is swapped: 8.6 ms (`status` costs about 40 µs per process here, `statm` 17 µs, `stat` 30 µs, listing `/proc` with each folder's owner 2 ms). The figures are of a hot loop; in the running TUI, every 2 s, the same sample takes 10 to 40 ms of the sampler thread's CPU, so the sample stays near 0.5 % of a core. Rejected after measuring: keeping each process's `stat` and `statm` open and rereading them with `pread` (5.8 ms in the loop, within the noise in the TUI, and 2 descriptors per process against the soft limit of 1,024 that cornercase's children inherit); stopping at a short read (no gain: the read that returns 0 is cheap). Not yet measured on macOS, where the source reads `KERN_PROCARGS2` of every process each sample and the same cache would apply.
- **macOS fields**: `proc_listallpids` lists the pids (asked once for the count, then with 64 spare slots for processes born in between). `proc_pidinfo(PROC_PIDTBSDINFO)` gives the parent, process group, real uid, name (`pbi_name`, or `pbi_comm` when empty) and start time (seconds and microseconds, the `started` value); a process whose BSD info cannot be read is dropped. `proc_pid_rusage(RUSAGE_INFO_V4)` gives `ri_phys_footprint`; if it fails the memory is `—`. `proc_pidinfo(PROC_PIDTASKINFO)` gives `pti_total_user + pti_total_system`, which are Mach absolute time units, not nanoseconds: they are converted with `mach_timebase_info` (1/1 on Intel, 125/3 on Apple Silicon; 1/1 if the call fails). If task info fails (zombies, processes the kernel hides) the CPU time is zero, so `cpu_percent` shows no figure or 0 % rather than a wrong one. `sysctl([CTL_KERN, KERN_PROCARGS2, pid])` into a buffer of `KERN_ARGMAX` bytes (1 MiB if unknown), allocated once per sample and reused for every process, gives the arguments and environment; if it fails (another user's process, a zombie) the arguments are empty and the variables unset.
- **`KERN_PROCARGS2` layout**: a native `i32` argc, the exec path, NUL padding, `argc` NUL-terminated arguments, then the environment (followed by Apple's own `key=value` strings, which are ignored like any other variable). The parser (`procs/procargs.rs`) is pure and compiled for tests on every platform: a buffer shorter than argc or without a NUL after the exec path yields nothing; argc larger than the strings present, a negative argc or a missing final NUL keep what is there. Empty leading arguments cannot be told from the padding and are lost (as in `ps` and psutil); with them, the first environment strings fill the missing argument slots. Only the displayed arguments and, at worst, the first variables suffer. The environment is parsed by the same `procs/environ.rs` as Linux's `environ`.
- **`libc`** gives `getuid` and `sysconf` (and, on macOS, `proc_pid_rusage` and `sysctl`). `rustix` was rejected: it covers Linux well but not the macOS calls, so it would mean two crates for the same job. `libc` also covers `proc_listallpids`, `proc_pidinfo` and `mach_timebase_info`, so the `libproc` crate was not needed; `mach_timebase_info` is deprecated in `libc` in favour of `mach2`, which would be a second crate for one call, so that one use is marked `#[expect(deprecated)]`. The `unsafe` calls are sound without further checks: `getuid` and `sysconf` have no preconditions; on macOS every buffer is passed with its real size, `proc_pidinfo` results are accepted only when the kernel wrote exactly the struct's size, the structs read back are plain integers (zeroed first, so `assume_init` is sound; a private `unsafe trait PlainData`, whose implementors promise that all-zero bytes are a valid value, limits the helper to them; it is marked `#[expect(clippy::missing_safety_doc)]` because the repo has no doc comments and this paragraph is its safety contract) and `sysctl`'s returned length truncates the buffer; in the tests, `mmap` is checked against `MAP_FAILED` and every access stays within the mapped length.
- **Killing** sits behind the `Killer` trait (`procs/kill.rs`: `term` and `term_group`, both given a `Target`: the pid, its start time and its process group as the last sample saw them), so the TUI is tested with a fake that records what it was asked; the real one sends `SIGTERM` with `libc::kill` (the call has no memory preconditions). Right before the signal it reads the process again (`/proc/<pid>/stat` on Linux, `proc_pidinfo(PROC_PIDTBSDINFO)` on macOS) and sends nothing, answering `Error::Ended`, unless the start time and the group still match: a sample can be a whole interval old, and in that time the pid may have been reused. The window left between that read and `kill` is microseconds; `pidfd_send_signal` would close it on Linux only and was not worth a second path. It refuses ids that `kill(2)` reads as something else: pid 0 (the caller's own group), group 0 and group 1 (`kill(-1)` signals every process the user owns), and anything above `i32::MAX`; and a group equal to its own (`getpgrp`, which cannot fail) or when it cannot tell its own. Its tests only signal `/bin/sleep` children the test spawns itself (one in its own process group), wait for them with `wait_until`, and kill and reap them on drop if an assertion fails first.
