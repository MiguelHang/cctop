# TUI

Code: `ui/`, `app/`

- **Two views**, switched with tabs at the top (click or `Tab`): **Processes** (the usage tree as a table: name, memory, CPU %, and for panes agent/status/context) and **Context** (the breakdown of the selected pane's Claude session: total and %, fixed vs dynamic bar, then the top files and commands). Selecting a pane in Processes and switching keeps it selected.
- **Mouse first**, like cornercase: click selects a row and folds or unfolds it on its arrow, a header click sorts by that column, the wheel scrolls. Keys exist too, since the pane is cctop's own: arrows, `Enter` (fold), `Tab`, `s`, `k`, `q`.
- **Refresh** every `interval` ([config](config.md)) on a background thread that samples and asks cornercase; the UI loop never blocks on I/O. Context is only read for the selected pane.
- **Killing** (`k`, or the row's menu) asks first with the process, its pid and its pane; it sends `SIGTERM` to the process (or its group, chosen in the dialog). Never without confirming.
- `ui` renders a `View` (plain data built by `app`) and returns hit areas for the mouse, so it is tested with snapshots and no I/O.
- **Processes layout**: a tab bar on the first line (`Processes`, `Context`; the active one reversed and bold) with the totals (`mem`, `cpu`) or the last error (red) right-aligned; a total that does not fit is left out whole (`cpu` first, then `mem`), never cut, since a cut number reads as a different one; then a bold header of clickable columns `Name`, `Memory`, `CPU`, `Agent`, `Status`, `Context`, the sorted one marked `▼`; then one line per visible row. Numbers are right-aligned, text left-aligned, one blank column between columns. Memory, CPU, Agent, Status and Context take fixed widths (9, 6, 8, 8, 9) and are added in that order only while `Name` keeps at least 16 columns, so at 40 columns only name, memory and CPU show; `Name` takes the rest. Rejected: ratatui's `Table`, because the mouse needs the same column rectangles the render uses.
- **Rows**: indented two columns per level, then `▾` (open), `▸` (folded) or nothing, then the label; anything too long is cut at the end with `…` and never moves the columns. The arrow's two cells fold, the rest of the line selects. Projects are bold, workspaces cyan, tabs blue, panes and processes plain; the hot path is yellow; the selected row is reversed across the whole width (reverse works on any terminal theme). Missing values show `—`, estimated memory `≈`. Agent, Status and Context are blank on every row that is not a pane, so `—` only means a pane without that value.
- **Stable row ids**: selection and folds are kept by id (`Project`, `Workspace`, `Tab` and `Pane` by cornercase's id, a process by pane and pid), never by line number, so they survive every refresh and re-sort. A selected row that disappears (its process ended) hands the selection to the row now at its place; everything starts unfolded. Rows carry their subtree's totals at every level, processes included, so a folded row still shows what it hides.
- **Sorting from the UI**: the tree sorts by `Memory`, `Cpu` or nothing (cornercase's order). Clicking `Memory` or `CPU` sorts by it, clicking `Name` goes back to cornercase's order (marked on `Name`), `Agent`, `Status` and `Context` are not sortable and ignore the click. `s` cycles memory → CPU → cornercase's order. The config's `sort` maps onto the tree's sort in `app`, the only place that knows both. Changing it rebuilds the tree from the last reading, without waiting for a tick.
- **Keys**: `↑`/`↓` move the selection (from nothing, `↓` takes the first row and `↑` the last), `PgUp`/`PgDn` by a page, `Enter` toggles the fold, `←`/`→` fold and unfold, `Tab`/`Shift-Tab` switch views, `s` sorts, `q` and `Ctrl-C` quit. The wheel scrolls three lines; moving the selection scrolls to keep it on screen.
- **Errors**: a reading that fails (cornercase not running, `status` unparsable, the process table unreadable) shows its message in red where the totals go and keeps the last good tree on screen; the next tick retries and clears it. A bad `config.toml` shows its first warning in the same place until the first key or click.
- **A hung `status`**: the cornercase client has no timeout, so the sampler thread is the only thing that can block on it; the UI loop only drains a channel and polls input every 250 ms, so it stays responsive and `q` quits at once (the sampler is not joined; a stuck `cornercase` child outlives cctop until it ends on its own). When no answer, good or bad, has arrived for three intervals (at least 5 s) the header says `cornercase has not answered for Ns`. Rejected: a timeout in `Runner` (a thread per call or a polling wait in the client) for a case that the thread already isolates.
- **Terminal**: alternate screen, raw mode and mouse capture are set on start and undone on any exit, including an error (a guard's `Drop`) and a panic (a hook that releases the mouse before ratatui's restores the screen).
