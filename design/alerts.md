# Alerts

Code: `alerts/`

- **The service** (`cctop watch`, the plugin's `[[service]]`, kept running by the cornercase server) samples every `alert_interval` and checks each pane's tree. Each round takes a process sample, then `status --json`, builds the usage tree (cornercase's order, no sort) and runs the rules; it then sleeps what is left of the interval, measured from when the previous round was due, so a slow round shortens the next sleep and a round longer than the interval starts the next one at once instead of bursting to catch up. A deadline the clock cannot represent sleeps the whole interval rather than panicking or spinning; config already caps durations at `24h`.
- **Thresholds** (`config.toml`, defaults in [config](config.md)): memory per pane and CPU per pane sustained for `cpu_sustain`. The figures are the pane's totals, the sum of its process tree. A pane is over a threshold when its total is strictly above it.
- **Hysteresis**: a pane alerts once when it crosses, then not again until it drops below 80 % of the threshold, so a tree hovering on the line does not spam. Memory and CPU are armed and fired separately. CPU counts from the first sample over the threshold and alerts once it has stayed over for `cpu_sustain` (the time between the samples, as the samples were taken, not the wall clock of the loop); any sample at or under the threshold, or with no CPU figure (the first sample has none), restarts the count, but only one under 80 % rearms. An unknown memory changes nothing.
- **New and gone panes**: a pane the rules have not seen starts armed, so a pane already over the threshold when it appears, or when the service starts, alerts on its first sample. A pane missing from a tree is forgotten at once: if its id comes back it counts as new. Rejected: keeping state for missing panes, which would grow without end and say nothing about a pane that is gone.
- **The message** names the pane's place, its total and the heaviest process with its own figure: `cctop: feat/x › claude 5.2 GB — cargo test 3.1 GB` (CPU alerts show percentages). The place is the workspace's name, else its branch, else `workspace <id>`; the pane is cornercase's agent, else its program, else `pane <id>`. The heaviest process is the one with the highest own figure of the alert's metric anywhere in the pane's tree (the same rule as the hot path), shown as its name plus its arguments after the first, cut to 40 characters; with no process figure only the total is shown. A memory total that misses some process's figure (`memory_partial`) is a lower bound and shows `≈`, as in the TUI. It is sent with `cornercase notify -- <text>` (the window's toast and a desktop notification).
- **Failures** never stop the service: a failed sample, `status` or `notify` writes one line `cctop watch: <error>` to stderr, which is the plugin's log, and the loop goes on. When `status` fails the sample is still kept, so the next round's CPU is measured against it, and the rules keep their state, so a pane over the threshold does not alert again when `status` comes back. A failed `notify` is not retried: the alert counts as sent, since a retry every round would repeat a toast that may have been shown.
- **A hung `status`**: the cornercase `Runner` has no timeout and the service adds none. A `status` that never answers blocks the loop, which is harmless: it is the same server that runs the service, a stuck server cannot show a toast either, and when it exits or restarts it stops and restarts its services. A timeout would need a thread or a child to kill per call for no gain.
- **Config** is read once when the service starts; its warnings go to stderr. A change takes effect when cornercase restarts the service.
- The decision logic is pure (state per pane + tree + instant → alerts) and tested on its own with series; the loop takes a `Runner`, a `ProcessSource`, a log writer and a `Clock` (now and sleep), so it is tested with fakes and a clock that only advances when asked.
