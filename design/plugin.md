# Plugin

Code: `cornercase-plugin.toml`, `cctop open`

- **A button that opens a popup**: plugins cannot draw inside cornercase's UI, so cctop runs in a terminal. The action `cctop` has the contexts `button`, `project`, `workspace`, `tab` and `pane` and `placement = "popup"`: cornercase's button **cctop** (and the entry in every menu) runs `target/release/cctop` itself in a popup over the window, which `q` or `Esc` closes by ending cctop (with code 0; another code would show as a failed action). No `width` or `height`: the popup takes 80 % of the window each way, and a table with seven columns and two graphs wants all the room it can get, which a fixed size would cap on a large window. The mouse reaches cctop because it asks for it (mouse capture), and every key reaches it, `Esc` included, which is why `Esc` can quit. The icon is `◔` (U+25D4), a gauge-like circle a quarter full: one cell, readable without a Nerd Font, and no glyph cornercase uses itself (its plain set has `▤` for Files, for one), so it cannot be mistaken for one of its buttons; the title `cctop` names it on hover.
- **The split stays, in the pane menu**: a second action, **cctop in a split** (`split`, context `pane`, the default `job` placement), runs `cctop open` as before (below), for keeping cctop beside a pane while working in it; a popup is modal and dims the window, so it is for a look, not for watching while typing elsewhere. It is offered only on a pane, where "beside it" is unambiguous; the popup covers the other menus. A project of its own, **cctop**, opened in the plugin's state folder, was tried first and dropped: it read as one more project in the sidebar and took the user away from where they were.
- **`min_cornercase = "0.12.187"`**, the first with buttons and popups: an older cornercase refuses the whole manifest over the `button` context, and would ignore `placement` and run the TUI as a job with no terminal. Rejected: a second manifest or keeping the split as the only action for older versions, since a plugin has one manifest and 0.1.0 is not published yet. `tests/manifest.rs` checks the rules cornercase applies to these fields (`plugins/manifest.rs`): one character one cell wide for the icon, known contexts, unique action ids, and `width`/`height` only on a popup and within 20 to 500 columns and 5 to 200 rows.
- **Where the popup starts**: see [TUI](tui.md) (starting at the launch place) and [usage tree](usage-tree.md) (cctop's own processes).
- **Which pane** (`cctop open`): the action's environment names what was clicked (`CORNERCASE_PANE` only for a pane, `CORNERCASE_TAB`, `_WORKSPACE`, `_PROJECT` for the rest and their parents); the narrowest one set wins, and none set (run by hand) fails saying `cctop open` is the menu's action. A pane is split as it is; a tab splits its active pane, a workspace its active tab's, a project its active workspace's, each falling back to the first when `status --json` marks none `active`. Something `status` does not list, or a tab without panes, is an error and nothing is split.
- **Reusing one**: before splitting, if a pane of that tab reports `program` `cctop` (its file name, so a full path counts too), it is focused (`focus --pane`) and no split is made, whichever pane of the tab was clicked. Only that tab is searched: cctop in another tab does not stop a new one here, since the point is to have it beside what the user looks at. No process is read: the action must stay instant and the pane's foreground program is what cornercase already knows; a pane that reports no program does not count.
- **Closing with `exec`**: `split` types its command into the new pane's shell, and cornercase removes a pane once its shell exits. Typing `exec <cctop>` makes cctop replace the shell, so quitting cctop ends the pane's only process and the pane goes, with no shell left behind; without `exec` a shell would remain and closing it would need `close --pane` from the TUI, which was rejected (the TUI would have to know it was opened by the action). The path is `std::env::current_exe()`, the same for `[[build]]` and `[download]`, quoted for the shell when it holds anything but plain path characters, since `split` joins its words with spaces. `exec` is understood by every shell cornercase starts (sh, bash, zsh, fish).
- **Services**: `[[service]] watch` runs `cctop watch` (alerts). The TUI is not a `[[window]]` process: those have no terminal; the popup gives it one.
- **Distribution**: `[[build]] cargo build --release --locked` always, and `[download.<target>]` for `x86_64`/`aarch64` Linux and macOS (the four targets cornercase knows) once a release exists. Each archive is `cctop-<target>.tar.gz` holding only `target/release/cctop` (mode `0755`, its folders, `ustar` with no macOS metadata, since cornercase refuses links and anything that is not a file or a folder): the same path `[[build]]` leaves, so the manifest's commands are one for both. Linux builds run on Ubuntu 22.04 (x86_64 and its arm runner, natively, no `cross`) so the binary needs only glibc 2.35; both macOS targets build on one macOS runner. Published with the `cornercase-plugin` topic, set by hand on the repository.
- **Screenshots** (`docs/screenshots/`, shown in the README): `make.sh` captures the release binary itself, not a separate render, so the images are what users get; it runs it in a private tmux (`tmux -L shots`, 120×34) and converts `capture-pane -e` to SVG with `ansi2svg.py`, which puts every cell at a fixed position and draws box lines, blocks and braille as shapes, so borders, bars and graphs line up whatever font the browser picks. Everything on screen is synthetic, since a screenshot of a real machine shows its projects, paths and processes: a fake `CORNERCASE_BIN` answers `status --json` with made-up projects (`scene.py`) and a `boot` of its own and ignores every other command, so the real cornercase is never asked or changed; the processes are `python3` under the names of `claude`, `cargo`, `rust-analyzer`… (symlinks, so the kernel names them after the link), shaped by `worker/sitecustomize.py` (memory in private anonymous maps, a duty cycle of CPU) and carrying that `boot` and their pane, so only they fall in the tree; the `claude` the Context shot shows writes its session file into a temporary `CLAUDE_CONFIG_DIR`, beside a transcript written by `transcript.py`; `HOME` and `XDG_CONFIG_HOME` are temporary too (the config sets a `100ms` interval, so three minutes fill the sparklines and part of the hour graphs). cctop runs pinned to four CPUs (`taskset`), since the CPU graph is a share of the CPUs it may use and on a large machine the scene's few cores would draw a flat line. Every process stops by itself at a deadline or when its parent goes, and the script's `trap` kills the scene's session and the tmux server and removes its folder on any exit. Linux only: the names and `/proc` mapping the scene relies on are Linux's. Rejected: rendering a `View` to SVG from a test, which would show a cctop that never sampled a process.
- **Releases** (`.github/workflows/release.yml`): a `v<version>` tag checks that it matches the version (`.github/versions.sh`), builds and packages the four targets (`.github/package.sh`), and publishes them with their `.sha256` files and the version's `CHANGELOG.md` section as a GitHub release. cornercase reads the manifest again from the installed commit and refuses one that differs from the preview, so the URLs and sha256 have to be committed: after publishing, the workflow rewrites the `[download.*]` tables (`.github/downloads.sh`) on the default branch and opens a pull request `chore: point downloads at v<version>`. The tagged commit itself has no downloads for its own version and builds; from the merge on, installs download. Committing straight to the default branch was rejected so a person sees the change, and building the archives before tagging to put their sha256 in the tagged commit was rejected because builds are not reproducible across runs. Only a pushed tag publishes; a manual run (`workflow_dispatch`), even with a tag selected, builds and uploads the archives as artifacts without publishing: the dry run. The tag's `CHANGELOG.md` section (`.github/notes.sh`) is checked before building, so a missing one fails in seconds rather than after the builds. Two limits of the pull request: it is opened with `GITHUB_TOKEN`, so the repository must allow GitHub Actions to create pull requests, and it does not trigger CI; to run the checks, close and reopen it or push an empty commit to its branch. Re-running the job updates the branch and reuses an open pull request.
- **Workflow hardening**: every action in `.github/workflows/` is pinned by commit SHA with its tag in a comment (`actions/checkout@<sha> # v7.0.1`), since a moved tag would otherwise run new code with the release's write token; a bump changes both together (resolve the SHA with `git ls-remote`). Checkouts drop the token (`persist-credentials: false`) except the one that pushes the downloads branch, and matrix values reach scripts through `env`, not `${{ }}` inside `run:`.
- **Versions**: `.github/versions.sh` (in CI's guardrails and the release) fails when `Cargo.toml` and `cornercase-plugin.toml` differ, when the tag is not `v<version>`, or when a `[download]` URL points at another version: a bump removes the `[download.*]` tables, otherwise installing the new version would unpack the old binary.
- **Permissions** declared: `read` (status), `notify` (alerts), `split` and `focus` (the split action; the popup needs none), so the preview is honest about what runs; `send` is not needed, since `split` types the command itself.
