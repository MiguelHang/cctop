# Usage tree

Code: `usage/`

- **Hierarchy**: project → workspace (branch, worktree or not) → tab → pane → process tree, in cornercase's sidebar order. Every level carries the sum of memory and CPU below it, so a collapsed project still shows its cost.
- **Pane roots**: a pane's processes are those mapped to it (see Cornercase client); the roots are the ones whose parent is not mapped to the same pane, normally the shell. Children are nested by parent pid.
- **Mapping**: a process takes `CORNERCASE_PANE`/`CORNERCASE_SERVER` from itself or, if it has neither, from its nearest ancestor that has one; it belongs to that pane only when the server equals `boot`. A pane without server, a snapshot without `boot`, another server's token or a pane id the snapshot does not list leave the process out (a parent cycle in a broken sample ends the walk). Processes outside every pane (the cornercase server itself, the rest of the system) are not in the tree.
- **cctop is not in the tree**: the TUI's sampler drops every process of cctop's own process group (`getpgrp`, the group the kill dialog already refuses) before the CPU, the tree and the agents are worked out, so cctop and the `cornercase status` children it runs never count. In cornercase's popup they would otherwise land in the pane on screen, since the popup's program gets that pane's `CORNERCASE_PANE` and `CORNERCASE_SERVER`; the popup's program leads a group of its own, so nothing else goes with it. Opened in a split with `exec`, cctop takes the place of the pane's shell and its group, so that pane shows no processes while cctop runs in it; started by hand from a shell with job control it is a group of its own too. A script that runs cctop without job control shares its group, and is hidden with it. Rejected: dropping cctop's own pid and its descendants, which needs the sampler's children to stay under it (a `cornercase` that forks a helper and exits would leave it in the pane), and keeping it with a mark, which still adds its cost to the pane's totals and alerts. The alerts service cannot use the group, since it is not in it: it drops cctop's actions by their environment instead (see [alerts](alerts.md)).
- **Hot path**: in each pane the most expensive process (memory, or CPU when sorting by CPU) and the chain of ancestors to it are marked, so `claude → bash → cargo test → test binary` reads at a glance.
- **Totals**: unknown memory (`—`, a kernel thread or zombie) adds nothing and sets `memory_partial` on every level above it, so the UI can show the sum as an estimate (`≈`). A level with no figure at all (an empty pane, or no CPU on the first sample) has no total (`—`), not zero.
- **Sorting** is chosen when the tree is built (`build(.., Option<Sort>)`): the app rebuilds it from the last snapshot and sample when the sort changes, so going back to "no sort" restores cornercase's order without remembering it. `None` keeps cornercase's order for every level and processes by pid; `Memory` or `Cpu` sorts every level (projects, workspaces, tabs, panes, sibling processes) by its totals, highest first, a missing total counting as zero. Ties keep cornercase's order (stable sort) and, between processes, the lower pid first.
- **Hot path ties**: the metric is the process's own figure (not its subtree's); without a sort it is memory. A process with no figure or zero never starts a hot path; on a tie the first in display order wins, an ancestor before its descendants.
- **Agents**: a pane shows cornercase's agent, status, model, context % and subagents count from `status`; nothing is guessed from process names that cornercase already knows.
- **One pane's processes** (`pane_processes`): the same mapping, flattened parents first and siblings by pid, for the app to find a pane's `claude` without building the tree.
- Pure: built from a `Snapshot` and a `Sample`, tested with fixtures.
