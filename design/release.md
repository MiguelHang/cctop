# Release check

Code: `release/`, the footer in `ui/`

- **Why cctop says it**: cornercase does not tell when a plugin has a new version; the user has to run `cornercase plugin update`. So cctop asks GitHub for its latest release (`api.github.com/repos/MiguelHang/cctop/releases/latest`, no token) and, when it is newer than its own version, the bottom border of the box on screen (the list box in Processes, the conversation box in Context) shows `0.2.0 available · cornercase plugin update cctop` on the right, in green, or `0.2.0 available` when the whole text does not fit, or nothing. The notice takes its room from the keys, which drop whole from the end as usual: a version that is out says more than a key the user already knows. Only the TUI checks; the `watch` service does not, so a notification never interrupts work for it.
- **At most once a day, never in the way**: the check runs on its own thread, started with the TUI, and the loop picks its answer up like the stale message (one draw when it arrives, none before). The popup starts cctop often, so the result is kept in `latest-release.json` in the state folder ([config](config.md)) with the time of the check, and a check of less than 24 h ago is not repeated; a time in the future (a clock set back) counts as old. A failed check (no network, rate limit, an answer that is not a release) is recorded too, keeping the tag known before, so being offline does not ask on every start and does not forget a known update. The file is written to a temporary name and renamed, so two cctops never read half of it. No state folder means no check.
- **Comparing**: the tag is read as `major.minor.patch` with an optional `v`; anything else (a pre-release, a name) never shows a notice, since `releases/latest` already leaves pre-releases out. Only a newer version shows, so right after updating the cached tag stops showing without asking again.
- **`curl`, not an HTTP crate**: the request is `curl --fail --silent --show-error --location --max-time 10`, behind the `Fetch` trait so tests use a fake. `curl` is on macOS and on nearly every Linux, and an HTTP client with TLS would add a dozen crates and build time for one request a day; a missing `curl` is just a failed check.
- **Turning it off**: `check_updates = false` in `config.toml` starts no thread and reads no file.
- **Later**: cornercase telling about updates for every plugin (it already knows each one's address and installed commit) would be better than each plugin asking on its own; worth proposing upstream. Until then this stays.
