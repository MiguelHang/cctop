# Context

Code: `context/`

- **Finding the session** (Claude Code, checked on 2.1.306): the `claude` process in the pane gives its pid and `CLAUDE_CONFIG_DIR` (else `~/.claude`). `<config>/sessions/<pid>.json` gives `sessionId` and `cwd` (re-read each tick: `/clear` changes the id). The transcript is `<config>/projects/<cwd with every non-alphanumeric character as '-'; past 200 characters cut, plus '-' and a hash>/<sessionId>.jsonl`, the rule cornercase follows (`design/context-use.md` there); the cut is at 200 UTF-16 units and the hash is JavaScript's 32-bit string hash (`h * 31 + unit`) in base 36, as cornercase computes it; when that path does not match (a long path, or a Claude Code that hashes another way), the folder is found by listing `projects/` for the session's file. A `sessionId` with anything but ASCII letters, digits and `-` is ignored, so a session file cannot point outside `projects/`. A missing or broken session file, or no transcript yet, gives no breakdown rather than an error.
- **Which process is a pane's `claude`** (`app/context.rs`): the pane's processes (mapped as in the usage tree) parents first, in pid order, and the first that is `claude` by name, by `argv[0]`'s file name, or `node`/`bun` running a script named `claude`. Parents first makes the agent cornercase started win over a `claude -p` it runs in a shell. `vim claude` is not one: only the program, or the script a runtime runs, counts. Its config folder is its own `CLAUDE_CONFIG_DIR`, else `.claude` under cctop's `HOME` (Claude's processes run as the same user); cctop's own `CLAUDE_CONFIG_DIR` is never used, since it says nothing of another process. `Sessions` is asked for that one `claude` only (an empty list when no pane is asked for or the pane has none, which drops the other readers), behind the `Contexts` trait so tests count what is read.
- **Loaded on every message** (the fixed part, `Breakdown::fixed`): the newest `attachment` of type `instructions` lists each loaded instruction file (`CLAUDE.md`, `AGENTS.md`, imports, `MEMORY.md`) with path and full content; `skill_listing`, `deferred_tools_delta`, `mcp_instructions_delta`, `agent_listing_delta` and `prompt_snapshot` (system prompt) are the rest. These are what every turn pays.
- **This conversation** (the dynamic part, `Breakdown::dynamic`), since the last `system`/`compact_boundary` (what came before is no longer in the context): `tool_use` blocks joined to their `tool_result` by id, grouped by file for `Read`, `Edit`, `Write` (`input.file_path`), by command for `Bash`, by pattern for `Grep`/`Glob`, and by category for the rest (user prompts, assistant text, subagents' results, other tools). Sidechain lines (`isSidechain`) are a subagent's own context and are left out.
- **Tokens**: the real total is the last assistant reply's `usage` (`input_tokens + cache_creation_input_tokens + cache_read_input_tokens`, a missing field counting 0), as cornercase computes its percentage; replies whose `model` is `<synthetic>` carry zeros and are skipped, and a `compact_boundary` forgets the total until the next reply, since the old one measured the context before the compaction. Each part is estimated as characters (Unicode scalar values) / 4, rounded up, then all estimates, fixed and dynamic together, are scaled so they add up exactly to the real total, the rounding going to the largest remainders; the parts are an `Estimate`; the view says so once, in a note, instead of a `≈` on every line, since the total next to them is real. Without a total the estimates are left unscaled; with a total but nothing estimated (every part empty), the parts stay at 0 and do not add up to it. The last reply's `usage` measures the input of that reply, so the reply itself and what follows it (its `tool_use`, the `tool_result`s) are counted in the dynamic part before the usage includes them; the scaling absorbs it. The `count_tokens` API was rejected for the MVP: it needs a key and network for a view that refreshes every few seconds. The scaling also spreads over the parts what the transcript does not show (tool schemas, Claude's own framing), which is preferred to a separate "unknown" part that would be most of the total.
- **Records** (`context/record.rs`, checked on 2.1.306): each line is parsed on its own into a `Record`, through `serde_json::Value` rather than typed structs, so a field of an unexpected type empties that field instead of losing the line. What counts of each:
  - `instructions`: per file, `path` and the characters of `content`; the newest attachment replaces the files before it. One whose `files` is not an array is `Other`, so a broken record never wipes the files already known.
  - `skill_listing` `content` and `prompt_snapshot` `systemPrompt` (its strings added up): the newest replaces the older one.
  - `deferred_tools_delta` (`addedNames`, `removedNames`), `mcp_instructions_delta` (`addedNames` paired with `addedBlocks`, `removedNames`) and `agent_listing_delta` (`addedTypes` paired with `addedLines`, `removedTypes`) are deltas kept by name: a name without its text weighs its own length. The `removed…` keys were not seen in a transcript and are read in case they appear.
  - User `content`, a string or `text` blocks, is a prompt; a `tool_result` block counts the characters of its `content` (a string, or the `text` of its blocks; images are not counted).
  - Assistant `text` and `thinking` are the replies; a `tool_use` counts its `input` serialised as JSON, and its `tool_result` is added to the same group when it arrives, joined by `id`/`tool_use_id`. A result whose use is not known (before the last compaction, or never seen) goes to the other tools.
- **Grouping**: `Read`, `Edit` and `Write` by `input.file_path`, `Bash` by `input.command` without a leading `cd <folder>; ` or `cd <folder> && ` (repeated, a quoted folder included), so `cd /x/y; git diff` shows and groups as `git diff`: Claude prefixes many commands with the folder it is already in, and the prefix hid the command behind a long path (only a `cd` at the start followed by `;` or `&&` and a command is dropped; a lone `cd`, a pipe or a `cd` later in the line stay as written); `Grep` and `Glob` by `input.pattern` (the `path` is left out so one search in two folders is one line), `Agent` and `Task` as subagents; a known tool without its key, and every other tool, as other tools. The fixed part keeps a fixed order (system prompt, instruction files in Claude's order, skills, tools, MCP, agents) and lists only what the transcript had; the dynamic part goes from the largest part down.
- **Groups** (`Breakdown::groups`): the parts of this conversation are joined by kind for the view: `Commands` (`Bash`), `Files` (`Read`, `Edit`, `Write`), `Searches` (`Grep`, `Glob`), `Claude's replies`, `Your messages`, `Subagent results` and `Other tools`, each with the sum of its scaled parts, from the largest group down and its parts from the largest down. Only commands, files and searches have parts of their own to list; the other groups are already one category each. The words are the user's ("loaded on every message", "this conversation"), not the code's ("fixed", "dynamic"), in the view, the README and here.
- **Reading**: the transcript is read as it grows (offset kept, a quiet tick costs one `stat`); a shrunk or replaced file (another device and inode) is read again from the start, with a new `Accumulator`. `Sessions` keeps one reader per pid with the session id it was opened for: the session file is read every tick, a new id opens a new reader, a pid no longer asked for drops its reader, and a transcript that cannot be read drops it too (the next tick starts again), while a missing session file keeps it, so the same id coming back does not read the transcript again. A failed read leaves the reader as it was (offset and partial line), so the next read picks up where it left off. While a session has no transcript yet, every tick looks for it again, listing `projects/` when the direct path misses: accepted for the MVP, since it only lasts until the first message; caching the miss by `(pid, sessionId)` and the mtime of `projects/` is the way out if it shows. A file rewritten in place to the same or a greater size is not detected; Claude only appends. The first read takes the whole file, since the fixed part sits at its beginning. The `Accumulator` takes records one by one and gives the same `Breakdown` however the lines are split between reads, but a line must be complete: the reader keeps a partial last line for the next read instead of handing it over, or that record would be lost as a broken line.
- The transcript is not a stable API: every record is parsed tolerantly, and a missing record makes its part `—` rather than an error. Fixtures are named by Claude Code version and written by hand in the shape seen there, never copied from a real transcript.
