# Cornercase client

Code: `cornercase/`

- **Only public commands**, run through `$CORNERCASE_BIN` (set for every plugin command; `cornercase` on the `PATH` when run by hand): `status --json` for the hierarchy, `open <path> --focus` and `new-tab --workspace ID --name cctop -- cctop` for the action, `focus`, `notify -- <text>` (the `--` keeps a text that starts with `-` from being read as a flag). No socket protocol of our own: the commands are cornercase's stable contract (`CONTRACT` 1, additive), and a newer cornercase keeps answering them.
- **`status --json` rather than `status --panes`**: the TSV is flat and lacks the tree's order of tabs and the project paths the action needs; the JSON gives both, plus `boot`. Parsing is tolerant: unknown fields ignored, every optional field `Option`, so a newer cornercase never breaks it.
- **What is read from `status --json`**: `boot`; `groups[].id`; per project `id`, `name`, `path`, `group`, `workspaces`; per workspace `id`, `name`, `branch`, `path`, `worktree`, `tabs`; per tab `id`, `name`, `panes`; per pane `id`, `agent`, `status`, `model`, `context` (as `context_percent`), `subagents`, `parent`, `program` (as `command`) and `path`. Only the ids are required: a missing id is an error, since nothing can point at that row; every other field is optional and missing becomes `None` (`worktree` false, lists empty). The fixture is hand-written in the shape of cornercase 0.12.173 (`control::status::Report`), never a real capture.
- **Sidebar order**: the JSON lists projects in the server's order, not the sidebar's. `Snapshot::parse` puts loose projects first (no group, or a group the answer does not list), then each group's projects in the order of `groups`, as cornercase's own `Report::loose` and `Report::grouped` do; within each part the JSON's order is kept.
- **Answers**: `open` prints the project's id and `new-tab` the new pane's id (not the tab's), parsed as a number; anything else is `Error::Answer`. A non-zero exit is `Error::Command` with the argv and the trimmed stderr. Paths are passed as text (`to_string_lossy`), since the `Runner` takes `String` arguments. An empty `CORNERCASE_BIN` counts as unset.
- **Mapping processes to panes**: every shell cornercase starts gets `CORNERCASE_PANE=<id>` and `CORNERCASE_SERVER=<token>`, and every descendant inherits them. The token is `<server pid>-<start ns>`, the same string as `boot` in `status --json`. A process belongs to pane N of this server when both match; a pane id alone is not enough, since a second server (a debug build of cornercase) numbers its panes from 1 too. A process that cleared its environment is attributed through its nearest ancestor that has them.
- **Runner**: the client runs commands through a `Runner` trait (argv in, stdout or error out), so tests answer with fixtures and never start cornercase. It has no timeout: a hung cornercase blocks the caller. Whether the TUI and the `watch` loop run it on a thread with a timeout is decided with them (tasks 010 and 013).
- **For a later pull request to the core**: `pid` (the pane's shell) and `memory` (the figure the tab row already computes) as optional fields of each pane in `status`. With them cctop would not need to read other processes' environment (the hard part on macOS), and other clients would get the memory too.
